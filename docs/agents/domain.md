# 领域文档

说明各工程技能在探索代码库时应如何使用本仓库的领域文档。

## 探索之前先读这些

- 仓库根目录的 **`GLOSSARY.md`**，或
- 若存在，仓库根目录的 **`GLOSSARY-MAP.md`**：它指向每个上下文各自的 `GLOSSARY.md`，阅读与当前主题相关的那些。
- **`docs/adr/`**：阅读涉及你即将修改区域的 ADR。多上下文仓库还要查看 `src/<context>/docs/adr/` 中限定于该上下文的决策。

上述文件若不存在，**静默继续**。不要指出它们缺失，也不要预先建议创建。`/domain-modeling` 技能（经由 `/grill-with-docs` 与 `/improve-codebase-architecture` 触发）会在术语或决策真正确定时按需创建它们。

## 文件结构

本仓库采用单上下文（single-context）布局：

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-xxx.md
│   └── 0002-xxx.md
└── lib/
```

如果日后拆成多个包/上下文，改为在根目录放 `GLOSSARY-MAP.md`，指向各上下文自己的 `GLOSSARY.md` 与 `docs/adr/`。

## 使用术语表中的词汇

当输出中提到某个领域概念（Issue 标题、重构提案、假设、测试名称等）时，使用 `GLOSSARY.md` 中定义的术语，不要换成术语表明确避免的同义词。

如果所需概念尚未收录，这本身就是一个信号：要么你在发明项目并不使用的说法（请重新考虑），要么确实存在空缺（记下来交给 `/domain-modeling`）。

## 标出与 ADR 的冲突

如果你的输出与现有 ADR 相矛盾，要明确指出，而不是悄悄推翻：

> _与 ADR-0007（订单事件溯源）相矛盾，但值得重新讨论，因为……_
